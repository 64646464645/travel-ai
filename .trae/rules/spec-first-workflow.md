# 功能实现流程规范

仅当需求属于中大型新功能、跨模块需求、公共 API 或数据库变更，或需求边界不清时，必须遵循完整 Spec 流程。已创建 Spec 的状态、文档一致性和验收证据由 `spec-lifecycle.md` 定义。

## 轻量任务

以下低风险、边界明确的任务可直接实施，不必创建 Spec：

- 单文件 Bug 修复或类型错误修复。
- 文案、样式和局部交互调整。
- 针对性测试补充。
- 不涉及公共 API、数据库或环境变量的局部文档和配置修改。

轻量任务仍须遵守核心工作区规则，并按变更风险执行必要验证。任务跨出上述范围、涉及专项规则，或实施中发现需求边界不清时，停止直接实施并回退到完整 Spec 流程。

## 完整 Spec 流程

完整 Spec 流程严格遵循以下三步，不得跳过或合并：

1. **先写 spec 文档**：使用 `spec-splitter` 技能将需求拆分到 `.trae/specs` 目录，生成 `spec.md`、`tasks.md`、`checklist.md` 三个文档。
2. **询问是否修改文档**：spec 文档写完后，先向用户展示文档内容并询问「是否需要修改文档」，等待用户确认。
3. **询问是否实现**：文档确认无误后，再询问用户「是否根据文档实现具体功能」，只有得到用户明确同意后才开始编码实现。

## 实现阶段（第 3 步确认后）

用户确认「根据文档实现」后，必须按以下流程执行，不得跳读或省略文档：

1. **定位并读取全部文档**：根据用户指定的 spec（或最近的 `.trae/specs/<日期>/<区域>/<slug>/` 目录），**必须同时读取** `spec.md`、`tasks.md`、`checklist.md` 三份文档，缺一不可。
2. **按任务逐项实现**：严格对照 `tasks.md` 的任务列表，按编号 T1、T2……逐项完成；每完成一项，同步在 `tasks.md` 对应行标注完成情况（如勾选或备注）。
3. **按检查清单自检**：编码完成后，必须对照 `checklist.md` 的「完成后验收」逐条自检，逐条确认通过后才算完成。
4. **汇报验收结果**：向用户汇报时，列出已完成的 `tasks.md` 任务编号，以及 `checklist.md` 验收项的通过情况；存在未通过项时，说明原因并修复至通过。

## 要点

- 每个阶段都必须停下来等待用户确认，不能连续执行多步。
- 未完成第 2、3 步确认前，不得直接修改业务代码。
- 完整 Spec 是其对应实现与验收的唯一依据，实现时严格对照 `tasks.md` 逐项完成，并按 `checklist.md` 完成验收。
